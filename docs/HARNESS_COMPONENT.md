# Lean Harness component

Vertex Studio ships a Windows-only, single-agent Harness component. The pinned
upstream checkout remains an independent development reference; its broad CLI
dependency list is not copied into the component.

## Removed from runtime and payload

- LibreOffice and Office-to-PDF conversion; Office and spreadsheet preview renderers.
- Experimental Inspector and its development assets (conversation trajectory stays).
- Local voice input, SenseVoice, and Sherpa ONNX.
- Non-Vertex model adapters and their OpenAI/Anthropic/provider SDK trees.
- Subagents, external agent runners, and delegation/PTC presets.
- Browser/computer automation adapters and browser sidebar.
- DeepSeek account login, cloud session upload, telemetry, and generated titles.
- Scheduled child-agent execution, which depends on the removed subagent service.

Files, PowerShell, approvals, Windows sandbox support, Skills, MCP, conversation
history, terminal, and changes remain in the component. Text, Markdown, HTML,
images, PDF and code previews remain registered. Registered tools now use the sandbox/approval pipeline; see HARNESS_FEATURES.md for the current writable capabilities.

## Rebuild

Build the pinned upstream once following HARNESS_INTEGRATION.md, then run from
the repository root with Node 24.18.0 and Python on PATH:

```powershell
node harness/build_component.mjs
```

The script transforms preview imports in memory, builds into `.runtime/lean-preview`,
and assembles a fresh `.runtime/harness-lean-<timestamp>` directory. It prunes
production dependencies, preserves runtime JavaScript definitions and native assets,
omits development dependencies/maps/test files, and rejects banned packages.
Node and upstream/third-party license notices remain included. No paid jobs run.

After offline acceptance, place the component in `harness/component/` for development
or `components/harness/` under the installed application data root. Startup regenerates
absolute plugin paths after relocation. Generated components are ignored by Git.

## Offline acceptance

```powershell
python harness/verify_component.py
```

This optional browser check requires Playwright and its Chromium browser in the
test Python environment. It uses a fresh test home/workspace under `.runtime`,
scrubs credential environment variables, uses the offline model, and shuts down
only its own test process. It verifies startup, new-session send, file read/tool
response, final answer, and actual preview registrations. It never uses live user
sessions or Google Cloud generation.

The active desktop is not restarted by the build script. Restart its backend to
load a newly selected component; existing sessions and credentials remain separate.

## Measured payload (2026-10-14)

The standalone Windows x64 component contains 333 distinct runtime packages.
Its measured ZIP payload is approximately 69.6 MB, versus approximately 192.8 MB
uncompressed, including Node. These are decimal MB and exclude the base image
studio installer. ZIP size is not a promise for a future NSIS installer.

Run `python harness/package_component.py` after placing the accepted runtime in
`harness/component/`. This creates a preview component ZIP and file checksums under
`.runtime`; the generated absolute-path profile is excluded and regenerated by
the Python backend at startup. This is a component payload, not an automatic
component installer or a new public Release.

## Editable persona

Harness Settings > Role and prompts provides a multiline role/style editor with
Save and Restore default. The value is persisted as `vbs-persona.json` under
`DSH_HOME` (normally `data/harness/home`). The adapter rereads it before each new
cloud model request, renders `{{model}}`, and adds it to system instructions ahead
of the unchanged Batch execution policy. Pending cloud inputs remain immutable.
This role/style override does not change tools, sandbox permissions or budgets.
The authenticated same-origin UI endpoint accepts 1–16000 nonblank characters;
writes use atomic replacement. Offline acceptance exercises save and reset without
contacting Google Cloud.

## Parallel function-response fix (2026-10-15)

Gemini parallel function calls now receive one user Content containing every
corresponding functionResponse in native call order. Native IDs, signed model
content, and tool-result bytes are preserved. Text/reasoning block coalescing does
not affect call/result association. Interleaved user context follows the complete
response group; missing, duplicate or orphan results fail locally before submission.

The recorded three-read failure was replayed offline with its exact frozen history.
The existing failed receipt remains immutable; this fix does not automatically
create another paid job. Offline Agent-loop acceptance now exercises three read
calls and the same request codec. Supported text attachment bodies are now preloaded into the initial request
by the application before model submission. The Agent build can now create a requested Markdown output file with its write tool, subject to the selected sandbox mode and approval.

## First-request text attachment preloading (2026-10-15)

Uploaded Markdown, TXT, JSON, CSV, and common code/text files are read locally
before the provider creates its immutable request. The complete decoded body is
inserted in the original user attachment position as JSON data, with filename,
byte count, SHA-256, encoding, and an explicit complete flag. The existing DSH
transcript and source attachment are not rewritten. The Batch policy tells the
model to use this provided body instead of requesting the same file again.

The preload is limited to 256 KiB per file and 512 KiB of unique file data per
request, preferring recently attached materials. Duplicate bodies are included
once. The DSH attachment store supplies bounded reads; the adapter also checks
canonical paths, byte counts, and full hashes. UTF-8 and BOM-marked UTF-16 are
supported. Credential JSON bodies are excluded. Unsupported formats, oversized
files and decoding failures have explicit incomplete status; content is never
silently truncated. PDF/Office document extraction is not enabled by this change.
Input token and budget checks still happen before cloud submission.

Acceptance covers the actual browser Markdown upload path, first-request body
inclusion without a read-tool round in the offline model, encoding/limits,
duplicate aliases, and a local replay using the user's 93,542-byte uploaded script.
No new Google Cloud job is created by these checks. Preloaded attachment data is
frozen with each request; already submitted jobs retain their original inputs.

## Unsupported video attachments

Video attachment cards are retained in the composer but decorated with a dark
mask, circled red exclamation mark and the label `不支持的文件类型`. Their remove
button remains available. Existing local uploads are allowed to remain in the
attachment store, but uploaded video handles are removed from user messages
before text preloading and Gemini request conversion; neither video bytes nor
the uploaded video's local path are sent to the model. The original transcript
and tool replay are not rewritten.

The shared `harness/plugins/attachment-policy.mjs` exports two independent code
switches: `showUnsupportedVideoOverlay` and `skipVideoAttachments` (both true).
The extension list also lives there; TypeScript `.ts` and `.mts` are deliberately
not classified as video by extension. Turning off the overlay only changes the
presentation. Turning off skipping does not implement native video input.
Enable actual video transmission only after its upload, MIME validation and
Gemini `fileData` conversion are implemented and tested.

The selected component has its own copy under `harness/component/plugins/`.
Synchronize source policy changes into that copy and restart Harness to apply
them. Future component builds copy these files automatically. Offline checks
cover the warning card, removal, video filtering, independent switches, regular
attachments, source-code extensions and preserved tool replay.
